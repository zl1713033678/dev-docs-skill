# 文档腐烂根因、真实度矩阵与排障门禁详解 (Anti-Rot Principles)

## 1. 为什么 90% 的项目文档会在两周内腐烂？

在快速迭代与 AI 辅助编程场景下，传统手工文档最常见的四大死法：
1. **补丁式追加（Append-Only Syndrome）**：每次迭代在 `HANDOFF.md` 末尾追加一节“本轮修复了 X”，却不修改前文“待解决 X 风险”的描述，导致同一份文档前后时空错乱。
2. **职责大杂烩（God-Document Anti-Pattern）**：把架构启停、产品竞品对比、用户手册、未落地的未来设想、已修复的几十条历史 Bug 塞进同一个 500+ 行文件。每次研发或 AI 会话被迫吞入大量无关噪音，稀释核心红线注意力。
3. **虚假完成幻觉（Mock-as-Done Illusion）**：前端画好了按钮、后端返回了硬编码模拟字符串，进度表就标上“已完成”。接手者误以为底层已通，上线或联调时才发现核心引擎为空壳。
4. **重复手抄代码事实（Duplicating Code Truth）**：手写几十张数据库字段表或全量路由参数表——只要改一次字段必与代码脱节。API 契约应交由 OpenAPI 自动生成，表结构应以 ORM 模型与迁移脚本为唯一事实源。

## 2. 读写分离设计哲学（按变更频率与读者解耦）

| 层级 | 文件路径 | 变更频率 | 维护动作 | 核心读者 | 行数上限建议 |
| :--- | :--- | :---: | :--- | :--- | :---: |
| **入口层** | `README.md` | 低频（架构/命令变动时） | 覆写刷新 | 新成员 / 外部访问者 | `≤ 100` 行 |
| **宪章层** | `AGENTS.md` | 低频（领域红线变动时） | 覆写精炼 | AI Agent / 核心研发 | `≤ 100` 行 |
| **状态层** | `docs/STATUS.md` | **高频（每轮交付必刷）** | **全量横截面覆写** | 跨会话接手人 / AI | `≤ 80` 行 |
| **缺陷层** | `docs/BUGS.md` | **高频（随发现与修复流转）** | **动态增删清零** | 排障研发 / QA | 仅留未修项 |
| **决策层** | `docs/adr/000X-*.md` | 极低频（重大取舍时新建） | 只增不改（废弃则标 Superseded） | 架构师 / 维护者 | 每篇 `≤ 70` 行 |
| **孵化层** | `docs/specs/SPEC-00X-*.md` | 中频（新点子立项与验收） | 一特性一文件 + 索引打卡 | 产品 / 研发 / AI | 按需独立承载 |
| **归档层** | `CHANGELOG.md` | 中频（每批修复/发版追加） | 按版本倒序追加 | 审计 / 发布回溯 | 不限（平时免加载） |
| **手册层** | `docs/guides/*.md` | 低频（交付/汇报节点更新） | 专题成册 | 终端用户 / 运维 / 汇报 | 按需独立承载 |

## 3. 模块真实度矩阵 (Truth Matrix) 评级标准

在 `docs/STATUS.md` 中评估任意业务模块时，必须基于**纯代码审计事实**授予等级：

- **`L1 [Demo模拟]`**：仅有静态 UI、前端假状态或后端固定字符串拼装返回，无真实持久化或核心计算。
- **`L1.5 [混合原型]`**：数据库持久化、基础权限或计费流水已跑通，但外部网关、硬件遥测或核心算法仍为启发式/模拟逻辑。
- **`L2 [逻辑闭环]`**：前后端真实业务逻辑、输入校验、RBAC 权限隔离与异常处理完整闭环，无硬编码假数据污染。
- **`L3 [测试加固]`**：在 `L2` 基础上具备自动化单元/集成测试（含核心不变量的属性测试 Property-Based Testing）以及并发锁（乐观锁/数据库排他约束）保护。
- **`L4 [生产就绪]`**：完成外部真实协议/API 对接、高熵密钥收口、性能压测、备份恢复演练与生产可观测性监控。

## 4. 科学排障 6 步闭环 (Red-Green Bug Gate)

1. **左移静态检查**：用 Linter / Typechecker 拦截语法、类型与弃用 API 问题。
2. **分级建单（`docs/BUGS.md`）**：明确 `S0`（越权/资损/数据损坏）、`S1`（主流程算错/并发丢更新）、`S2`（边缘偏差）、`S3`（UI 体验），记录精确 `file:line` 与取证数据。
3. **先写必败测试（Red）**：修改任何业务代码前，先写最小自动化测试复现该 Bug 并亲眼确认 `FAIL`，证明定位到真根因。
4. **原子化最小修复（Green）**：单次修复只解决该 Bug，严禁搭车修改无关样式或重构其他模块，确保测试由红变绿且全量回归通过。
5. **属性不变量验证**：涉及资金账本、配额、状态机流转时，使用属性模糊测试（如 Python `Hypothesis` / JS `fast-check`）验证任意操作序列下守恒律恒成立。
6. **清零归档**：将已修复条目从 `docs/BUGS.md` 移除，记入 `CHANGELOG.md` 并更新 `docs/STATUS.md`。
